# Vanilla WoW Client / Multiboxing

`vanilla-wow-client/client.sh`

Configures and launches multiple vanilla WoW (1.12.1) game clients under Wine on a single Linux PC, for multiboxing. Companion to [Vanilla WoW Server](vanilla-wow-server.md) but entirely independent — it never touches the server, only the client(s) that connect to one (this repo's own server or any other vanilla-family realm on the LAN).

- **Wine runtime is Bottles (Flatpak, `com.usebottles.bottles`)**, not a host-layered `wine`/`wine-core` package — on immutable/atomic hosts (e.g. Bazzite) a layered `wine-core` needs a reboot and its `wineboot --init` has been observed to hang indefinitely on some builds. Bottles bundles its own known-good runner, needs no reboot, and being a Flatpak works the same way on any distro with Flatpak+Flathub
- **Multiple simultaneous instances**: each instance ("box") gets its own Bottles bottle (a real, independent Wine prefix — registry/DirectX state can't collide) and its own WTF/Cache/Logs (account state, saved vars, addon cache can't collide either)
- **Two file-isolation modes**, picked once in `configure`: `full` (a complete copy of the client per instance — more disk, but avoids the read contention/disconnects that many Wine processes hitting a symlink-shared install can cause at higher instance counts on one SSD) or `shared` (symlinks the large/static client directories and gives each instance only its own private WTF/Cache/Logs/Errors/Screenshots/realmlist.wtf — minimal disk use, best at low instance counts)
- **Each instance launches WoW.exe directly** in ordinary decorated windowed mode (sized via `Config.wtf`'s `gxWindow`/`gxResolution` cvars) — not wrapped in a Wine virtual desktop, since that wrapper is itself a borderless window that some window managers force-fullscreen regardless of requested size (a compatibility heuristic for legacy fullscreen games), defeating multi-box tiling
- **Window identity for key broadcasters**: since dropping the virtual desktop wrapper loses its built-in title-naming, `launch` spawns a small background "title keeper" that finds the window this instance just created (a before/after window-ID diff, since Wine doesn't reliably expose `_NET_WM_PID`/a unique `WM_CLASS` for this) and re-asserts its title to the instance name every couple seconds for as long as the game runs — a stable, unique handle to target regardless of what the game itself shows in its own title bar. Requires `xdotool`
- **LAN realm discovery**: `discover-realm` scans the local `/24` for hosts with the realm port (3724 by default) open — via `nmap` if installed, a parallel pure-bash `/dev/tcp` sweep otherwise — and lets you pick one to prefill `configure`. This is a port probe, not a full protocol handshake (mangos-family forks differ enough at that level to make one unreliable); it's always just a prefill you can override manually
- **`launch`** re-renders each instance's realm every time (its own override if set, otherwise the global default) — both the client-root `realmlist.wtf` (vanilla 1.12 reads it from there, not `WTF/`) and any cached `SET realmList`/`SET realmName` cvars in `WTF/Config.wtf`, which some client builds prioritize over `realmlist.wtf` entirely — so a `configure`/`edit-instance` change is never silently stale on the next launch
- **`winecfg`**: opens the standard Wine configuration GUI scoped to one instance's bottle, an escape hatch for DirectX/sound/DLL tuning this script doesn't attempt to guess for every distro/Wine build
- **`stop`** kills via `wineserver -k` scoped to that instance's own bottle, with a `pkill` fallback on the instance's own client path (observed `wineserver -k` occasionally leaving the outer wine process alive after the game itself exited) — each bottle's `wineserver` is independent, so this can never affect a different instance's process tree
- Commands: `install-deps`, `configure`, `discover-realm`, `add-instance`, `list-instances`, `edit-instance`, `remove-instance`, `winecfg`, `launch`, `stop`, `stop-all`, `status`. The interactive menu groups these into categories (Setup, Instances, Launch, Status)
- Account creation/login itself isn't handled here — same as real WoW, that happens in the client's own login/character-creation screens against the server
